# v1.0.49 CI v1.0.45 장기 세션 측정 격리 핫픽스

## 증상

100-wave 브라우저 검증에서 목표 웨이브, 런타임 오류, 힙·텍스처·지오메트리 증가량과 WebGL 복구는 통과했지만 `frameP95`와 `longTasks`만 실패했다.

## 원인

기존 브라우저 하네스는 5웨이브마다 `gc()`를 직접 호출한 직후 10프레임만 측정했다. 강제 GC와 관찰자 전달 지연은 게임 플레이가 아니라 검증기가 만든 제어 작업이지만, 바로 뒤의 짧은 프레임 표본과 전역 long-task 누적값에 포함됐다.

10개 프레임 표본에서는 단일 GC 정지 프레임이 p95와 사실상 같은 위치를 차지한다. 100웨이브 동안 반복된 강제 GC는 long-task 증가량도 실제 플레이 부하보다 크게 만들 수 있다.

## 수정

- 강제 GC를 측정 구간 밖의 명시적 안정화 단계로 이동했다.
- GC 뒤 observer turn과 렌더 settle frame을 기다린다.
- 각 표본을 24프레임으로 확대하고 앞의 3프레임을 warm-up으로 제외한다.
- long-task 판정은 실제 측정 프레임 창에서 발생한 delta만 누적한다.
- 전체 브라우저 long-task 값은 `rawLongTasks`와 `rawLongTaskMs`로 보존해 진단 정보가 사라지지 않게 했다.
- 실패 시 실패 체크, 실제 metrics, thresholds, 최악의 프레임 표본 5개를 출력한다.
- 동일 패턴을 사용하던 v1.0.46 브라우저 릴리스 검증에도 같은 격리를 적용했다.
- v1.0.46 dist 검증을 현재 v1.0.49에서도 동작하는 `1.0.46+` 계약으로 수정했다.

## 변경하지 않은 기준

성능 기준은 완화하지 않았다.

- frame p95 한도: 34ms
- frame p95 추세: 10웨이브당 1.5ms 이하
- measured long-task 증가 한도: 12개
- 힙·텍스처·지오메트리 증가 및 추세 한도: 기존 값 유지

실제 측정 창에 50ms 이상의 프레임 정지가 반복되면 새 하네스에서도 실패한다.

## 2차 CI 재현 결과와 보완 (2026-07-29)

위 1차 GC 격리는 필요했고 그대로 유지한다. 다만 GitHub Actions의 실제 실패 로그에서는 격리 이후에도 SwiftShader 소프트웨어 렌더러가 약 200ms 간격으로 프레임을 공급했고, 측정 프레임 대부분이 Long Task로 기록됐다. 따라서 GC 오염 제거만으로는 CI 실행기 자체의 절대 렌더링 속도와 실제 게임 회귀를 구분할 수 없었다.

이번 보완은 임계값을 전역 완화한 것이 아니다.

- 실제 하드웨어 또는 렌더러가 불명확한 환경: 기존 `frame p95 <= 34ms`, `long-task 증가 <= 12` 절대 기준 유지
- SwiftShader/llvmpipe 등 명시적 소프트웨어 렌더러: 초기 표본 대비 p95 비율·증가량·정규화 기울기와 `long-task / measured-frame` 비율의 악화 여부로 판정
- 요청 프레임 수 미달 또는 측정 timeout: 렌더러 종류와 관계없이 실패
- 런타임 오류, WebGL context 손실/복구 불균형, 힙·텍스처·지오메트리 증가 기준: 기존 기준 유지

실제 실패 로그의 p95 216.6ms는 높지만 10웨이브당 기울기가 -5.497ms로 악화가 아니었고, 런타임 오류 0건, context loss/restore 1:1, heap/texture/geometry 기준도 통과했다. 이 유형은 소프트웨어 렌더러의 안정적인 느린 기준선으로 분리한다. 반대로 동일 수치를 하드웨어 프로필로 입력하거나, 소프트웨어 렌더러에서도 기준 대비 악화율이 한도를 넘으면 계속 실패한다.

세부 계약과 회귀 픽스처는 `docs/HOTFIX_v1.0.49_V145_CI_MEASUREMENT.md`를 따른다. 이 절의 2차 판정 규칙이 위의 "변경하지 않은 기준" 설명보다 우선한다.
